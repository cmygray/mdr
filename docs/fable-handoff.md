# mdr 1단계 — macOS 리더 앱 구현 지시

## 왜 만드는가

원(Won)은 마크다운 문서를 많이 읽습니다. 지금 쓰는 QuickMD는 빠르지만 한글 본문이 잘 읽히지 않고 디자인이 아쉽습니다. mdr는 QuickMD만큼 빠르면서 한글과 영문 모두 더 잘 읽히는 읽기 전용 리더입니다. 나중에는 원격 Linux 호스트의 Rex 터미널에서 `mdr file.md` 한 번으로 Mac·iPhone 앱에 문서를 띄웁니다. 이번 작업은 그 첫 단계인 **macOS 앱(로컬 파일만)** 입니다. 1단계가 끝나면 원은 같은 문서를 QuickMD와 나란히 띄워 가독성을 직접 비교합니다. 그러니 1단계의 결과물은 그 비교를 할 수 있는 실행 가능한 앱입니다.

설계 전체와 확정된 결정은 `docs/handoff.md`에 있습니다. 먼저 읽으십시오. 그 문서의 "확정된 결정"은 다시 논의하지 않습니다. 이후 대화에서 추가로 확정된 사항은 아래와 같습니다.

- 프로젝트 위치는 `~/src/mdr`, 앱 이름은 `mdr`입니다.
- 이미지는 표준 마크다운 문법 `![alt](상대경로)`만 지원합니다. Obsidian의 `![[name]]`은 지원하지 않습니다.
- 비교 기준 문서 3개는 `fixtures/`에 있습니다.
  - `01-korean-handoff.md`: 한국어 장문, 표, 목록, 인라인 코드
  - `02-english-readme.md`: swift-markdown README, 영문과 코드 블록
  - `03-images-typesetting.md`: 한국어 장문, `fixtures/images/`의 상대 경로 이미지 3개, 표, 깊은 제목 단계 (처음에는 다른 사람의 글을 번역한 문서였고, 2026-11-23에 저장소를 공개하려고 새로 쓴 글로 바꿨습니다)
- 아직 정하지 않은 것(CLI 언어, iPhone에서 Tailscale이 꺼져 있을 때의 경험)은 1단계와 관계없습니다. 정하지 마십시오.

환경: Xcode 26.2, Swift 6.2.3, macOS 26. `/Applications/QuickMD.app`이 있습니다. Pretendard는 설치되어 있지 않습니다. 번들할지는 라이선스(OFL)와 앱 크기를 확인한 뒤 결정하고, 근거를 기록하십시오.

## 완료 조건

1. 공유 Swift Package(파서 → 블록 모델 → 스타일 해석기)와 그 위의 얇은 macOS 앱이 빌드됩니다. iOS 앱은 3단계이지만, Package에 AppKit 전용 코드가 들어가지 않게 합니다.
2. fixture 3개가 모두 열리고, `docs/handoff.md`의 조판 원칙 1~5가 적용되어 보입니다. 특히 다음을 확인합니다. 한글 어절 단위 줄바꿈, 본문 폭 제한과 가운데 정렬, 제목 modular scale과 위아래 여백 차이, 코드 블록 가로 스크롤, 표, 상대 경로 이미지, 목차 사이드바, 문서별 스크롤 위치 기억, 라이트·다크 테마.
3. 스타일 토큰 파일을 고치면 앱이 다시 시작하지 않고 바로 다시 그립니다.
4. 각 fixture를 mdr와 QuickMD로 연 스크린샷을 `output/compare/`에 나란히 저장합니다. 원이 이 스크린샷을 보고 비교합니다.
5. 큰 문서를 여는 속도를 측정해 QuickMD와 비교합니다. fixture를 이어 붙여 약 1MB 문서를 만들어도 됩니다. 측정 방법과 수치를 기록하십시오.
6. 빌드 방법, 실행 방법, 토큰 편집 방법을 `README.md`에 적습니다.

완료 조건 2~5의 판단은 스크린샷과 측정값으로 닫으십시오. 코드를 읽고 "될 것"이라고 판단하지 마십시오.

## 작업 방식

이 코드베이스의 소유자이자 장기 유지보수자는 당신입니다. 설계는 당신이 정합니다. 다만 `docs/handoff.md`의 확정된 결정 안에서 정합니다.

`~/src/mdr`에서 `git init`을 하고 의미 있는 단위로 로컬 커밋하십시오. remote 추가와 push는 하지 않습니다. `~/src/mdr` 밖의 파일은 수정하지 않습니다. 단, QuickMD 실행과 스크린샷 촬영은 괜찮습니다. 앱을 띄워 확인한 뒤에는 앱을 종료하십시오.

진행 중에 알게 된 것, 내린 설계 판단과 이유, 남은 일은 `docs/progress.md`에 적으십시오. 다음 세션은 이 파일부터 읽습니다. 이미 코드나 git 기록에 있는 내용은 적지 않습니다.

## 서브에이전트와 토큰 비용

원의 사용량에는 상한이 있습니다. 서브에이전트 하나는 브리핑과 탐색을 처음부터 다시 하므로, 같은 일을 직접 할 때보다 토큰을 몇 배 씁니다. 그래서 다음 기준으로 판단하십시오.

- 위임할 가치가 있는 경우: 서로 독립적이고 읽을 양이 많은 조사(예: TextKit 2 attachment view provider의 동작, swift-markdown API 확인)를 병렬로 돌릴 때. 그리고 마일스톤마다 새 맥락의 검증자가 스크린샷과 완료 조건을 대조할 때. 새 맥락의 검증은 자기 검토보다 결과가 좋습니다.
- 위임하지 않을 경우: 파일 몇 개 읽기, 대상이 분명한 조회, 직접 고치는 편이 빠른 수정.
- 읽기 위주의 조사는 `model: "sonnet"`, 단순 검색은 `model: "haiku"`로 실행하십시오. 설계 판단과 최종 검증만 당신의 모델로 합니다.
- 서브에이전트는 당신의 맥락을 모릅니다. 목표, 이미 확인한 것, 읽을 파일, 돌려받을 형식을 짧게 주십시오. 실행 중에는 기다리지 말고 다른 일을 하십시오.
- 동시에 실행하는 서브에이전트는 보통 2~3개 이하로 두십시오.

맥락 창은 충분합니다. 맥락이 부족할까 봐 작업을 줄이거나 새 세션을 제안하지 마십시오.

## 끝까지 진행하기

원은 실시간으로 보지 않습니다. 완료 조건을 모두 채울 때까지 멈추지 말고 진행하십시오. 빌드 오류, 타임아웃, 실패한 도구 같은 평범한 장애는 원인을 진단하고 다른 방법으로 해결하십시오. 되돌릴 수 있고 이 지시에서 나오는 작업은 묻지 않고 진행합니다. 여기에는 다시 시도하기, 의존성 추가, 파일 생성·수정, 로컬 커밋이 포함됩니다. 확정된 결정과 정말로 충돌하는 문제를 만나면 멈추지 말고, 가장 덜 위험한 선택을 하고 `docs/progress.md`에 이유를 적은 뒤 계속 진행하십시오. 턴을 끝내기 전에 마지막 문단을 확인하십시오. 아직 하지 않은 일의 계획이나 약속이라면, 지금 그 일을 하십시오.

## 보고

응답은 한국어 하십시오체로 씁니다. 진행을 보고하기 전에, 각 주장을 이 세션의 도구 결과와 대조하십시오. 확인하지 못한 것은 확인하지 못했다고 쓰십시오. 테스트가 실패하면 출력과 함께 그렇게 쓰십시오.

최종 보고의 독자는 도구 호출과 파일을 보지 못한 사람입니다. 첫 문장에 결과를 쓰십시오. 그다음 비교 스크린샷과 속도 측정 결과의 위치, 원이 직접 판단해야 할 것(예: 글꼴 짝, 행간 값), 다음 단계 순서로 씁니다. 작업 중에 만든 약어나 용어는 쓰지 말고 풀어서 쓰십시오.
